# EcholIKE 工程红线卡

这张卡优先于便利性、默认流程和任何“顺手一起做”的判断。出现不确定时，停在本地并向用户确认。

## Git 远端红线（最高优先级）

- 默认禁止一切会改变远端 Git 状态的操作。
- 未获得用户在**当前任务**中的明确授权时，严禁执行 `git push`，包括普通推送、`--force`、`--force-with-lease`、`--mirror`、推送 tag，或由脚本/CI/发布命令间接触发的推送。
- 严禁新增、删除或修改 `git remote`、remote URL、上游分支和推送目标。
- 用户说“本地提交”“提交一下”“commit”时，只授权本地 `git add` / `git commit`；**不等于**授权 `git push`。
- 用户说“发版”“发布 OTA”“上传安装包”时，只授权对应发布链路；**不等于**授权 Git 远端推送。
- 即使用户已经在较早对话中授权过推送，也必须在当前任务再次明确确认；授权不跨任务自动延续。

## 允许远端推送的最低条件

只有用户明确说出“可以 push / 推送远端”，且推送目标没有歧义时，才可以执行普通推送。执行前仍需确认：

1. 待推送的本地 commit；
2. 目标 remote 与 branch；
3. 推送不会携带未审阅或无关提交。

强制推送、镜像推送、remote 修改和 tag 推送必须取得单独、逐项的明确授权，不能从普通 `git push` 授权中推断。

## Worklog 与 OTA 工作树红线

- 任何改动、新增、部署或发布都必须同步更新根目录 `WORKLOG.md`，并保持最新条目在前。漏写 worklog 时不得宣告完成或提交 OTA。
- 每次 OTA 构建/发布前必须运行 `git status --short`。本任务所属改动（包括版本号和 worklog）必须先本地提交，默认达到全仓 clean。
- OTA 请求仅授权为满足上述门禁而提交本任务自己的改动，不授权 `git push`。
- 若 dirty 文件属于用户或其他 agent，不得擅自 add/commit、回滚、stash、移动或隐藏；不得为了形式上的 clean 破坏他人工作。
- 外来 dirty 改动不是中断 OTA 的理由。允许按当前工作树继续打包，但必须在 worklog 逐项披露文件、归属、是否进入产物和验证结果；此时只能声明“本任务改动已 clean”，不能谎称全仓 clean。
- 若外来改动导致实际编译失败，应保留现场并报告具体失败；不得仅以工作树不干净为由提前停止任务。

## 违例处理

- 不要用“发布需要”“脚本会自动做”“已经登录”作为推送理由。
- 若发现命令可能隐式推送，先停止并改用不含远端 Git 写入的方式。
- 如果真的发生远端写入，立即如实报告操作、目标和结果；不得掩盖或补做其他远端操作。
