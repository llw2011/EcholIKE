# EcholIKE 屏幕与附件识别扩展计划

## 背景

当前 PDF 转 Markdown 能力已经在线上：图片、PDF、纯图片 PDF 都可以通过上传附件进入 OCR 链路，并输出可复制、可下载的 Markdown。下一步会出现两个自然扩展：PDF 转单/多页图片，以及 Markdown/OCR 结果导出 Word。

为了避免首页变成零散工具箱，后续能力统一归类到“屏幕与附件识别”。用户心智是先选择输入来源，再选择输出结果，而不是为每一种格式单独找入口。

- 2026-07-03：Phase 2 已完成，上传 PDF OCR 后可从附件处理结果中导出页面图片；单页导出 PNG，多页导出 zip 图片包。
- 2026-07-03：Phase 3 已完成，屏幕/附件识别结果可导出 `.docx`；标题、列表、表格会映射为 Word 原生结构。
- 2026-07-03：Phase 4 已完成，首页能力说明与结果弹窗出口已对齐，避免用户误以为只能导出 Markdown。
- 2026-07-03：Phase 5 已完成，二进制导出增加空文件保护与导出互斥，避免误报成功或并发点击导致状态混乱。

## 产品归类

入口统一为“屏幕与附件识别”。

输入来源：

- 屏幕截图：调用系统截图工具，用户框选区域后 OCR。
- 附件上传：图片、PDF、纯图片 PDF。

输出结果：

- Markdown：当前主能力，支持复制、下载 `.md`、继续追问。
- 图片：已支持，将 PDF 页面导出为单页图片或多页图片包。
- Word：已支持，将 Markdown/OCR 结果导出为 `.docx`，尽量保留标题、列表、表格。

## 当前边界

- 已支持：图片/PDF/纯图片 PDF OCR 到 Markdown。
- 已支持：Markdown 预览、复制、下载 `.md`、基于结果提问。
- 已支持：PDF 直接导出图片；单页为 PNG，多页为 zip 图片包。
- 已支持：导出 `.docx`；标题、段落、列表、表格优先转为可编辑 Word 内容。
- 不把 PDF 转图片称为 AI 能力；它是附件预处理/导出能力。

## 分期计划

### Phase 1：命名与信息架构收口

- 首页卡片从“AI 看窗口”收口为“屏幕与附件识别”。
- 上传入口从“上传附件识别”调整为“上传附件处理”。
- OCR 结果里把非上传来源称为“屏幕 OCR”，避免继续绑定“当前窗口”。
- 保持当前 Markdown 输出能力不变。

验收：

- 强制 OTA 锁定时，截图识别和上传附件处理仍会被禁用。
- 截图 OCR 后结果标题能正确显示为屏幕识别结果。
- 上传图片/PDF 后仍能进入 Markdown 结果弹窗并下载 `.md`。
- 基于 OCR 结果提问时，问题和上下文描述使用“屏幕内容/屏幕 OCR”或“附件内容/附件 OCR”。

### Phase 2：PDF 导出图片

- 在附件处理结果弹窗中为 PDF 来源提供“导出图片”。
- 单页 PDF 直接保存一张图片。
- 多页 PDF 输出多张图片，优先打包为 zip。
- 图片文件命名使用原 PDF 文件名加页码。

验收：

- 文本 PDF 和纯图片 PDF 都能按页导出图片。
- 导出的图片顺序稳定，页码清晰。
- 导出失败时不影响 Markdown OCR 结果。

### Phase 3：导出 Word

- 以 Markdown 结果作为中间格式生成 `.docx`。
- 标题、段落、列表、表格分别映射为 Word 原生结构。
- OCR 质量不足时保持可编辑文本优先，不强行还原复杂版式。

验收：

- 常见表格能在 Word 中成为可编辑表格。
- 多页 PDF 的 Markdown 内容能汇总到一个 `.docx`。
- 导出 Word 不改变现有 `.md` 下载行为。

### Phase 4：能力说明与出口闭环

- 首页“屏幕与附件识别”说明同步展示 Markdown、Word、PDF 页面图片三个出口。
- 上传附件处理中间态不再只暗示“纯 Markdown”，而是提示后续可导出 `.md` 或 Word。
- 结果弹窗保持一个主流程：复制、下载 `.md`、导出 Word、PDF 来源额外导出图片。

验收：

- 首页卡片文案不会落后于已经上线的导出能力。
- 用户上传附件时能明确知道识别后还有 Word 导出。
- PDF 页面图片导出仍只在 PDF 附件结果中出现，不污染普通图片或屏幕识别结果。

### Phase 5：导出可靠性补强

- 二进制导出返回空文件时不创建下载，也不提示成功。
- 导出 Word 与 PDF 页面图片互斥执行，避免连续点击造成重复下载或状态错乱。
- 失败提示保留在当前结果弹窗内，不影响已识别出的 Markdown 内容。

验收：

- 空文件导出会提示失败，不会触发浏览器下载。
- Word 导出中不能同时触发 PDF 页面图片导出，反之亦然。
- 导出失败后仍可继续复制、下载 `.md` 或重新导出。

### Phase 6：Markdown 与 Word 兼容性补强

- Markdown 表格解析支持单元格内的转义竖线 `\|`，避免预览和 Word 导出切错列。
- DOCX 文本输出会清理 XML 不允许的控制字符，避免 OCR 噪声导致 Word 文件损坏。
- 前端 Markdown 预览与后端 Word 导出保持一致的基础表格拆分行为。

验收：

- 表格单元格中出现 `A \| B` 时，预览和 Word 中都显示为 `A | B`。
- OCR 文本混入不可见控制字符时，导出的 `.docx` 仍可被 Word 打开。
- 普通表格、标题、列表和 `.md` 下载行为不回退。

### Phase 7：导出文件名安全化

- Markdown、Word、PDF 页面图片导出统一清理文件名里的非法字符。
- 避免 `CON`、`PRN`、`COM1` 等 Windows 保留名直接作为下载文件名。
- 导出基础文件名限制长度，避免超长原文件名导致保存失败或系统截断异常。

验收：

- 上传 `CON?.png` 后下载 Markdown，文件名应变为 `CON-file.md`。
- 上传包含路径符号和多余空白的 PDF 后，导出的图片包和 Word 文件名可正常保存。
- 超长文件名导出时保留可读前缀，并控制在稳定长度内。

### Phase 8：多页 Word 版式补强

- 多页 PDF OCR 结果中的页标题导出 Word 时保留为标题。
- 从第 2 页开始，在页标题前插入 Word 分页符，避免多页内容挤成一段长文档。
- 同时兼容中文 `第 N 页` 和英文 `Page N` 页标题。

验收：

- 多页 PDF 的 `.docx` 打开后，第 2 页及之后的内容从新页开始。
- 单页图片、单页 PDF 和普通屏幕 OCR 导出 Word 不额外插入分页。
- 现有标题、表格、列表、代码块导出不回退。

### Phase 9：分页触发条件收口

- 前端导出 Word 时把 OCR 的 `page_count` 传给后端导出命令。
- 后端仅在 `page_count > 1` 时启用页标题分页逻辑。
- 普通屏幕 OCR 或单页附件中即使出现 `第 2 页` / `Page 2` 文本，也不会被误判成多页 PDF。

验收：

- 多页 PDF 导出 Word 时，第 2 页及之后仍会分页。
- 单页/屏幕 OCR 导出 Word 时，页码样式文字只作为普通标题保留。
- Phase 8 的分页体验和普通文档的原样导出同时成立。

### Phase 10：OCR 尾部噪声清理

- 后端 OCR 文本清洗阶段移除末尾空代码块。
- 后端 OCR 文本清洗阶段移除末尾孤立竖线行，避免表格识别后的残留符号污染导出。
- 前端渲染、复制、下载 Markdown、导出 Word 前也复用同一类轻量清理，防止旧结果或异常返回漏网。
- 保留正文中真实的代码块和 Markdown 表格，不做过度清理。

验收：

- 结果末尾出现空的 ```/~~~ 代码围栏时会被清理。
- 结果末尾出现单独的 `|` 行时会被清理。
- 正文中的有效代码块、表格和标题不受影响。

## 设计原则

- 首页只保留一个附件入口，避免新增“PDF 工具”“Word 工具”等并列入口。
- 先保证 Markdown 结果可靠，再逐步增加导出格式。
- 转图片和转 Word 都从附件处理结果弹窗中扩展，不抢主流程。
- 未完成能力不在主界面伪装成可用按钮。
